# commit: コミットは承認制

## 原則

**承認者(ユーザー)の明示的な承認を得るまで `git add` / `git commit` を実行しない。**
他の Skill(issue-plan / create-pr 等)や作業フローの途中であっても例外なし。
「作業が終わったから流れでコミット」は禁止 — 必ず一度止まって案を提示する。

## 手順

1. **変更の確認**: `git status` と `git diff --stat` で変更内容を把握する
2. **案の提示**: 以下をまとめて承認者に提示し、**止まる**
   - コミット対象のファイル一覧(含めないファイルがあればその理由も)
   - コミットの分割案(意味のある単位。1コミットで良ければその旨)
   - 各コミットのメッセージ案(Conventional Commits: `feat:` / `fix:` / `docs:` / `ci:` / `chore:` など。件名は日本語で分かりやすく)
3. **承認待ち**: 承認者が「進めて良い」を選択するまで実行しない。
   選択肢は原則 3 つ — **進める / 修正して再提示 / 中止**
4. **実行**: 承認された内容**どおり**にコミットする。
   - 対象ファイルは明示的に `git add <path>` する。`git add -A` / `git add .` は
     承認した一覧と完全に一致すると確認できる場合のみ
   - 承認後に新たな変更が発生したら、混ぜずに再提示する

## やってはいけないこと

- 承認前の `git add` / `git commit`(提示と実行を1ターンで済ませない)
- 承認された一覧にないファイルの混入(node_modules・ビルド成果物・.env は特に注意)
- 承認なしの `--amend` / rebase / reset 等の履歴改変
- development / main 上での直接コミット(ブランチは new-branch Skill 参照)

コミット後に push する場合は **push Skill** の承認フローへ(自動では進まない)。
