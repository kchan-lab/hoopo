## 目的

家族間で「同じお子さんを同じ状態で見られる」ことを保証し、家族の設定から自分の連携を解除できるようにする。

## 方針

- **整合の担保(テスト)**: 父が提出した参加予定・コーチが付けた済ハンコ・お知らせが、母のセッションでも同じに見える
  (attendance / fees / announcements は child 単位のデータなので、guardian 間で一致する)。Integration で固定する
- **自分の連携を解除**: 家族の設定の「あなた(父)」行に「連携を解除」(二段階確認)。`DELETE /family-links/:childId` → 自分の
  guardian_children 行を削除。**その子に他の active な保護者がいないときは解除できない**(孤児化を防ぐ。409)
- **連携時の重複登録の案内**: 分岐画面(はじめての方)の招待コード欄の上に「すでに家族が登録済みなら、お子さんを新しく登録せず
  招待コードで連携してください(同じ子が二重に登録されるのを防ぐため)」の注記を出す
- **管理側**: 認定管理の家族連携カードはそのまま。解除は認定管理に「連携解除(保護者本人)」として出さない(削除なので履歴に残らない。
  必要になれば 実行ログ化を検討)

### API 契約

- 保護者 API `DELETE /family-links/:childId` → 204 / 404(自分の連携でない)/ 409(最後の保護者)
- 関数: `unlinkChild(teamId, guardianId, childId)` → `{ ok: true } | { ok: false, reason: "not_found" | "last_guardian" }`(`registration.ts` に追加)

### 設計判断

1. **解除は物理削除**: 無効化(revoked)はコーチによる事後確認の意味を持つので、本人の解除と区別する。再連携は招待コードで可能
2. **最後の保護者は解除不可**: 子どもが誰からも見えなくなるのを防ぐ。卒団・退団の削除フローは #21
3. **実行体制**: プランはメインセッション、実装は Opus サブエージェント(#83 と並列)。DB を使う検証と PR はメイン

## 完了条件

- Integration: 2人の保護者で提出・月謝・お知らせ・名簿が一致、解除の 204/404/409
- E2E: 父が登録→母が連携→母の家族の設定で解除→母のホームから子が消える、父は解除できない(最後の保護者)
