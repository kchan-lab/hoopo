# Plan: 日程管理をカレンダーからまとめて登録できるようにする

Issue: [#135](https://github.com/kchan-lab/hoopo/issues/135)
Sub-issue: [#141](https://github.com/kchan-lab/hoopo/issues/141)(135a: API)/ [#142](https://github.com/kchan-lab/hoopo/issues/142)(135b: admin UI)
設計の正: docs/REQUIREMENTS.md §5.2(日程管理)・§7(practices)/ CLAUDE.md 絶対原則 6(管理 UI)・開発ルール(日付は Asia/Tokyo 固定)
関連プラン: practice-schedule(現行の行入力と API)/ schedule-publish(発行)/ line-send(送信)

## 目的

月に十数コマある練習日を、1 日 1 行ずつ手で足す運用をやめる。カレンダーで日を選び、
よく使う時間帯・場所を選んで、まとめて登録できるようにする。

## 方針

```
[月のカレンダー(管理)]
 日 月 火 水 木 金 土     ← 曜日見出しをタップでその曜日を全選択/全解除
  ・ ・ ・ ・ ・ ✓ ✓      ← 練習が無い日をタップで選択(複数可)
  ✓ = これから作る日 / ● = すでに練習がある日(タップで従来の編集へ)

[選択したら下に出るバー]
 「3日を選択中」 [プリセット: 土日 9:00-12:00 粉浜小 ▼] [開始][終了][場所] → まとめて追加

           ↓ POST /practices/bulk(1 トランザクション)

[従来の行一覧]も残す(1 コマだけの追加・修正・メニュー入力・削除はこれまでどおり)
```

プリセットは**過去の practices から集計**する。新しいテーブルは作らない。

### 設計判断

1. **カレンダー入力は既存の行入力を置き換えず、並べて足す**: 行入力はメニュー・備考の編集や
   1 コマの修正に必要で、発行(schedule-publish)も行一覧を前提にしている。まとめ登録は
   「月初にまとめて作る」場面だけを担当し、細部は従来の行編集に委ねる。退けた案: カレンダーに
   一本化(メニュー編集の置き場所が無くなり、既存の E2E・発行導線の作り直しになる)。
2. **プリセットは専用テーブルを作らず、過去の practices から集計して返す**:
   直近 6 か月の (start_time, end_time, location) を件数の多い順に最大 5 件返す。
   新テーブルは team_id と RLS の追加・マイグレーション・管理 UI を伴うのに対し、
   実運用では「土日 9-12 粉浜小」のような数パターンの繰り返しなので集計で足りる。
   退けた案: team_schedule_presets テーブル(将来プリセットに名前を付けたい要望が出たら再検討)。
3. **まとめ登録は専用エンドポイント `POST /practices/bulk` を 1 トランザクションで**:
   1 日ずつ POST を繰り返すと途中で失敗したときに中途半端な月が残る。まとめて作り、
   全件成功か全件失敗にする。1 回の上限は 31 日(1 か月ぶん)。
4. **同じ日に既に練習がある日も選べる**: 午前と午後で 2 コマある運用があり得るため禁止はしない。
   ただしカレンダー上で「●(既にある)」と分かるようにし、選択時は「この日はすでに 1 件あります」と
   注意を出す。DB にも一意制約は足さない(既存どおり)。
5. **メニューはまとめ登録では入力しない**: 練習ごとに違うものなので、まとめ登録後に
   行編集から足す。まとめ登録のフォームは 開始・終了・場所・備考 の 4 つに絞る。
6. **曜日見出しのタップでその月の同じ曜日をまとめて選ぶ**: 「毎週土日」という実際の使い方に
   一番効く操作。プリセットと組み合わせると、月の練習が 2 タップ+1 回の保存で作れる。
7. **日付・曜日は Asia/Tokyo 固定の既存ヘルパ(monthGrid / weekdayOf)を使う**:
   保護者アプリのカレンダーと同じ純関数で、UI だけ管理用のモノトーンにする。
8. **Sub-issue 2 本に分ける**: 135a(API: bulk 作成・プリセット集計・テスト)、
   135b(admin UI: カレンダー・選択バー・プリセット・E2E)。135b は 135a の契約に依存する。

## API 契約(135b が依存)

- `GET /practices/presets` → 200 `{ presets: { startTime, endTime, location: string | null, count: number }[] }`
  直近 6 か月の実績を件数降順・最大 5 件。実績が無ければ空配列(UI は既定値 09:00-12:00 を出す)
- `POST /practices/bulk` → body `{ dates: string[], startTime, endTime, location?, note? }`
  - 201 `{ practices: Practice[] }`(作成順は日付昇順)
  - 400: 日付が 1〜31 件でない / 日付形式が不正 / 月をまたぐ指定 / 時刻の検証エラー(既存の parsePracticeInput と同じ文言)
  - 作成は 1 トランザクション。menus は空で作る(設計判断 5)

## 完了条件

- 曜日見出しのタップで月内のその曜日が選択され、プリセットを選んでまとめて登録できる(E2E)
- まとめ登録が 1 トランザクションで、途中の失敗で 1 件も作られない(Integration)
- プリセットが過去の実績から件数順に返る(Integration)
- 既存の行入力・発行・LINE 送信・出欠が従来どおり動く(既存 E2E がグリーン)
- 新しいテーブル・マイグレーションを追加しない
