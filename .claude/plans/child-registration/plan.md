## 目的

保護者の初回登録(1回だけの入力)→自動認定→コーチへの通知、招待コードによる家族連携、
管理側の認定管理・部員管理を貫通させる。スキーマ・RLS・招待コード生成・resolve_invite_code
関数は #6 で実装済みのため、**新規マイグレーションは原則なし**で API と画面を積む。

## 方針

```
[保護者(portal)]
初回ログイン(#23) → 子ども0件なら分岐画面(ワイヤー15)
  ├ 新規登録: ①子ども情報(兄弟複数可) → ②参加情報 → POST /children(自動認定 status=active)
  └ 招待コード: コード入力 → POST /family-links(resolve_invite_code → guardian_children 作成)
家族の設定(ワイヤー14): 招待コード表示・コピー、連携済み家族一覧

[コーチ(admin)]
認定管理: 登録・連携の履歴一覧(新着順)+「無効化」          ← これが「コーチへ通知」の実体
部員管理: 一覧(名前/呼び名/学年/性別/保護者数/伝達事項)+行詳細
```

### 設計判断

1. **「コーチへ通知」はアプリ内通知(認定管理画面)で実現し、LINE 送信はしない**:
   §6 の必須通知(予定表発行・リマインド)に登録通知は含まれず、個別 push は
   絶対原則3「通数原則」と「してはいけないこと」に抵触する。認定管理の履歴一覧
   (created_at 降順)が通知の実体で、ダッシュボードのバッジ表示は #30 のスコープ。
   既読管理テーブルは持たない(§7 にも定義がなく、事後確認の運用に既読は不要)。
   ドキュメント先行で REQUIREMENTS §3・§5.2 に「通知=管理画面での確認」を明記する。
2. **認定履歴の「経由元」はレコード種別から導出し、カラムを追加しない**:
   新規登録=children の作成、家族連携=guardian_children の作成(2人目以降)で
   ワイヤー PC-5 の「登録用URL経由/招待コード経由」を表現できる。source 列の追加は
   導出可能な情報の重複になるため退けた。
3. **登録用 URL の追加トークン検証はしない**: LIFF リンク自体が LINE グループ内
   限定の共有物で、§3 の部外者対策は「自動認定+事後確認(コーチが無効化)」が正。
   URL トークンを足すと保護者の導線に配布・失効の運用が増え、絶対原則2に反する。
4. **続柄(relation)は登録フロー②と連携画面に入力欄を追加する**: guardian_children.relation
   は NOT NULL でワイヤーに入力欄がないのは仕様の穴。セグメント(父/母/祖父母/その他)で
   1タップ入力とし、REQUIREMENTS §3 に追記する(ドキュメント先行)。
5. **兄弟・姉妹は①で複数登録、②の参加情報は全員に同一適用**: ワイヤー②は1子分の
   フォームであり、兄弟は同じ送迎事情である場合が大半。個別の調整は将来の
   部員詳細編集(スコープ外)に譲る。時間帯は単一レンジを選択曜日ぶん展開して
   child_availabilities に保存(UI 1レンジ → 曜日×行)。
6. **招待コードは実装済みの10桁(Crockford Base32)を正とし、表示は 5-5 ハイフン区切り**:
   ワイヤーの `MH7K-42QD`(8桁)は例示とみなす。入力は大文字化・ハイフン/空白除去で
   正規化(I/L/O/U は文字集合に無いので誤読の余地が小さい)。UNIQUE 衝突時の
   再生成リトライ(コメントだけで未実装)をこの Issue で実装する。
7. **resolve_invite_code の公開ヘルパを packages/db/client.ts に追加**: 生 db は非公開の
   方針を守り、`resolveInviteCode(code)` として escape hatch を関数単位で公開する
   (0001 のコメント「escape hatch はこの2関数に限定」と整合)。
8. **無効化(revoke)の意味論**: 認定管理の「無効化」は、新規登録カード→ children.status、
   家族連携カード→ guardian_children.status を revoked にする。保護者 API は
   「active な guardian_children 経由で見える子」だけを返すため、revoke で即座に
   閲覧不能になる(セッション自体は失効させない — 何も見えなければ実害がないため)。
   復帰 UI は作らない(誤操作時は SQL で戻す。運用実績を見て判断)。
9. **認証ガードを共通化**: `/me` にインライン展開されているセッション検証を
   requireGuardian / requireCoach ミドルウェアとして packages/api に切り出す。
   #12 で保護ルートが一気に増えるため、ここで整えるのが最小コスト。
10. **portal の UI 基盤(§1 トークンの globals.css)をこの Issue で新設**: admin(#24)と
    同じ素の CSS 変数方式。薄いオレンジ・iOS ネイティブ調・タブバーは今回は
    登録導線に必要な範囲のみ(5ボタンのフル実装は #13 以降)。
11. **admin のサイドバー(PC)/ドロワー(モバイル)レイアウト基盤もこの Issue で新設**:
    認定管理・部員管理の2画面が最初の住人になる。§5.1 の2レイアウト必須要件。
12. **Sub-issue に分割して実装する**(issue-plan の運用に従い親 #12 に紐付け):
    - **12a: 保護者の登録導線**(portal UI 基盤+分岐・登録①②・招待コード連携・家族の設定+API)
    - **12b: 管理の認定管理・部員管理**(admin レイアウト基盤+2画面+revoke API)
    12a が先行(12b は 12a のデータがないと画面が空)。PR も分ける
    (ブランチは 12a=`feat/child-registration`、12b=`feat/member-management`。プランは本ディレクトリを共用)。
13. **DB に依存しない定数・型・バリデーションは `@hoopo/api/shared` に分離する**(実装時の追加判断):
    portal のクライアントコンポーネントが続柄・曜日ラベルや `parseRegistration` を import すると、
    `@hoopo/api` のエントリ経由で `@hoopo/db` → `postgres`(Node 専用)がブラウザバンドルに
    入り、`next dev` が落ちる。`registration-shared.ts` を `./shared` エクスポートで公開し、
    DB を触る関数(`registration.ts`)と分けた。`@hoopo/db/invite-code` も同様に純粋なサブパスで公開する。
    招待コード生成は `node:crypto` ではなく Web Crypto(`crypto.getRandomValues`)に揃えた
14. **E2E は AutoLogin の固定ユーザーではなく、フェイク ID トークンで毎回別の保護者としてログインする**:
    同じ DB で繰り返し実行しても「未連携の保護者」から始められる(`context.request.post('/api/auth/line')`
    で Cookie を張る)。第二保護者の連携は保護者Aを API で作り、Bをブラウザで操作する
15. **招待コード衝突のリトライはネストしたトランザクション(SAVEPOINT)で行う**: 一意制約違反は
    トランザクション全体を abort するため、`tx.transaction()` の中で INSERT し、衝突時はそこまで
    巻き戻して別コードで再試行する(上限5回)

- 初回ログイン後、子ども未連携の保護者が「新規登録」または「招待コード」で子どもと紐づく

- 保持情報が §3 の項目のみであることをスキーマ・API 入力の両面で確認

- 部員管理に一覧+行詳細(伝達事項全文・曜日/時間・招待コード)が表示される
- Unit(コード正規化・衝突リトライ)/ Integration(登録・連携・revoke・RLS 越境)/
  E2E(登録→認定管理に表示、コード連携)がグリーン
