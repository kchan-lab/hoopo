# Plan: 予定表画像を1画面に収まるレイアウトにする

Issue: [#204](https://github.com/kchan-lab/hoopo/issues/204)
設計の正: `docs/REQUIREMENTS.md` §6(予定表画像)/ §10 未決事項、`docs/DESIGN_GUIDELINES.md`

## 目的

予定表画像を、スマホで一目で1か月分を見渡せる縦横比にする。
現状は1日1行の縦一列で 2026年9月が 720×1480px、10月が 720×1524px(縦横比 約1:2.1)。
1か月の予定はすべて入っているが縦に長く、全体を一度に見られない。

## 方針

**2カラム構成にする。** 左カラムに月の前半、右カラムに後半を置き、「1日1行」は維持する。

```
┌────────────────────────────────────────┐
│ SKC粉浜・北粉浜ミニバスケットボール      │ ヘッダー
│ 2026年10月 練習予定                     │
├──────────────────┬─────────────────────┤
│  1 木            │ 17 土 9:00-13:00 …  │
│  2 金            │ 18 日 13:30-17:00 … │
│  3 土 9:00-13:00 │ 19 月               │
│  …               │ …                   │
│ 16 金            │ 31 土 9:00-13:00 …  │
├──────────────────┴─────────────────────┤
│                        powered by hoopo │ フッター
└────────────────────────────────────────┘
```

### 設計判断

1. **2カラムにする(退けた代替案あり)**: カレンダー型(7列×5〜6行)は俯瞰性は最も高いが
   1マスが狭く「18:30–21:00 住吉中学校」が入らず、時間と場所を略記する必要があって情報量が落ちる。
   練習日だけを並べる案は最も短くなるが「何日が休みか」が読めなくなり、REQUIREMENTS §6 の
   「1ヶ月を1日1行」からも外れる。2カラムなら1日1行を保ったまま縦が約半分になり、
   現行アプリの見慣れた体裁からの距離が最も小さい。

2. **分割は `ceil(日数/2)` で前半・後半に割る**: 固定の「1〜15日 / 16日〜月末」だと31日の月で
   右カラムが16行になり左右が不均衡になる。`ceil` なら左右の行数差は常に最大1行に収まる。

3. **幅を 720 → 1024 に広げる**: 2カラムにすると1カラムあたりの実効幅が約360pxとなり、
   「喜連西小学校(練習試合)」のような長い場所名が入らない。1024 なら1カラム約512pxで収まる。
   **LINE 側の画像サイズ上限は未確認なので、広げる前に必ず確認する**(確認できない場合は
   720 のままカラム内のフォントサイズ・列幅で詰める案に切り替える)。

4. **高さは左右カラムの高いほうで決める**: 同じ日に複数コマあると行が伸びるため左右の高さが揃わない。
   `scheduleImageHeight` を「行数(number)を受け取る」形から「rows を受け取る」形に変え、
   分割 → 各カラムの高さ → `max` の順で計算する。既存シグネチャは壊れるが、
   レイアウト変更そのものが目的なので温存しない(Unit テストも合わせて書き換える)。

5. **色・書体・デザイントークンは変えない**: CLAUDE.md 絶対原則6(保護者側=薄いオレンジ)と
   `apps/portal/app/globals.css` のトークンに従う。今回変えるのは配置だけに限定し、
   配色や書体の刷新は混ぜない(1 Issue = 1 関心事)。

6. **`docs/REQUIREMENTS.md` §6 を実装より先に更新する**: 現行の記述
   「1ヶ月を1日1行で並べ」「現行アプリ『縦型カレンダー』の見慣れた体裁を踏襲」に抵触するため、
   CLAUDE.md「仕様変更はまずドキュメントを更新してから実装する」に従う。
   あわせて §10 未決の「予定表画像の細部デザイン(現行スクリーンショットの共有待ち)」は
   現行アプリのスクリーンショットが共有されて前提が揃ったため、扱いを整理する。

7. **satori の制約を守る**: `next/og`(satori)は flexbox のみを解釈する。
   `display: flex` を明示し、テキストは末端要素に置く(既存 `schedule-image.tsx` の方針を踏襲)。
   grid は使えない。

8. **文字は可能な限り大きくする(利用者の要望)**: スマホのカメラロールに保存して見返す用途
   (#203)と、LINE のトークで縮小表示される前提の両方で読めることを優先する。
   現状は 日付 20px / 曜日 15px / 時間・場所 16px / チーム名 28px / 月 20px / フッター 13px。
   2カラム化で横に余裕が生まれるぶんを文字サイズに回す。
   **文字を大きくすると行の高さ(`SCHEDULE_ROW_HEIGHT` 44px)も上げる必要があり、
   縦が再び伸びて「1画面に収める」目的と衝突する**ため、幅・文字サイズ・行高さの3つを
   セットで決める。判断の順序は「読めること > 縦横比」とし、
   縦横比は 1:1.2 以内を目標にしつつ、読めないサイズまで縮めない。
   最終的な値は実画像を生成して目視で決める(定数を1回で当てにいかない)。

## 完了条件

- 1枚の画像に1か月すべての日が入り、縦横比が概ね 1:1.2 以内に収まっている
- 文字が現状より大きくなっており、LINE のトーク上の縮小表示でも読める
- 31日ある月、同じ日に2コマ以上ある月、28日の月でレイアウトが崩れない
- 計算した画像サイズと実際の描画内容が一致している(下端に不自然な余白が出ない)
- LINE のトークに送ったときに読める大きさで表示される
- `docs/REQUIREMENTS.md` §6 の記述が実装と一致している
- Unit / Integration / E2E が green
